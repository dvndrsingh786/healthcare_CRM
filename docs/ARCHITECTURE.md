# Architecture

## Overview

A **modular monolith**: one FastAPI process and one PostgreSQL database, split into domain
modules with clear boundaries so a module could later become its own service. Routers are thin;
business rules, SQL and object-level checks live in each module's `service.py`.

```
app/
  config.py          settings from environment variables (12-factor)
  database.py        SQLAlchemy engine (PostgreSQL via psycopg 3), sessions in UTC
  errors.py          ApiError + the single error envelope
  middleware.py      request ID, security headers, access log, crash guard
  logging_setup.py   JSON logs with redaction
  security.py        passwords, tokens, the principal, permission checks
  audit.py           writes append-only audit events
  rate_limit.py      PostgreSQL-backed fixed-window rate limits
  storage.py         private file storage adapter, signed links, malware-scan hook
  messaging.py       email/SMS/push provider abstraction (console provider in sprint 1)
  metrics.py         in-process counters: the hook for a real metrics system
  modules/
    health/          liveness + readiness
    auth/            login, refresh rotation, logout, password reset, current user
    users/           staff users, roles, teams, service accounts + API keys
    organisations/   tenant settings (time zone, retention placeholders, notification policy)
    patients/        patients, emergency contacts, app accounts; access.py = who sees which patient
    assignments/     staff/team assignments and caseloads
    appointments/    appointments and their lifecycle history
    tasks/           follow-ups
    notes/           interactions/notes with visibility classes and revisions
    consents/        append-only consent evidence
    documents/       document metadata, upload/confirm, signed download
    timeline/        chronological patient timeline across modules
    notifications/   outbox, templates, worker
    summary/         CRM dashboard counts
    audit/           audit search
    app_api/         the patient app's API boundary (/api/v1/app)
migrations/          numbered SQL files, each with an up and a down section
tests/               pytest, runs against a throwaway database
```

## Key decisions and assumptions

| Topic | Decision |
|---|---|
| Stack | Python 3.11+, FastAPI, PostgreSQL 16+/17, SQLAlchemy Core with hand-written parameterised SQL (no ORM entities are ever returned). |
| IDs | UUID v4 generated by PostgreSQL (`gen_random_uuid()`), never sequential. |
| Time | All timestamps are `TIMESTAMPTZ` stored in UTC; DB sessions run with `timezone=UTC`. API input needs an explicit offset. Appointments also keep their IANA time zone. |
| Tenancy | Every business table has `organisation_id`. Every query filters by the caller's organisation, taken from their session, never from the request. |
| Migrations | Plain SQL, applied by `migrate.py`. Each file runs in one transaction (PostgreSQL DDL is transactional) and has a `-- migrate:down` section. A test rolls everything back and re-applies it on an empty database. |
| Errors | `{"error": {"code", "message", "request_id", "fields"}}` with stable codes (`VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `VERSION_CONFLICT`, `INVALID_TRANSITION`, `RATE_LIMITED`, `TEMPORARY_FAILURE`, ...). No stack traces or submitted values are echoed. |
| Concurrency | Patients, appointments, tasks and notes carry a `version`; edits must send the version they read (`409 VERSION_CONFLICT`). State changes lock the row (`SELECT … FOR UPDATE`). |
| Search | Indexed PostgreSQL only: trigram (`pg_trgm`) index for name search, b-tree indexes for every list filter. No search engine. |
| Observability | Every request gets an `X-Request-ID` (a safe incoming one is kept). Logs are JSON with the request ID; sensitive keys, bearer tokens and signed links are redacted, and the access log never writes query strings. `/api/v1/health` (liveness), `/api/v1/health/ready` (database). `app/metrics.py` counts requests and security events for a future exporter. |
| Security headers | `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, strict CSP on API routes, HSTS in production. CORS is an explicit allow-list (`CORS_ORIGINS`). |

## Authentication

- Passwords are hashed with **Argon2id** (`pwdlib`). Unknown emails are checked against a dummy hash, so response time does not reveal which accounts exist.
- Sessions use **opaque random tokens**, stored only as SHA-256 hashes: a short-lived access token (`ACCESS_TOKEN_MINUTES`, default 15) and a refresh token (`REFRESH_TOKEN_DAYS`) that is **rotated on every use**. Reusing an old refresh token revokes the whole session. Revocation (logout, logout everywhere, deactivation, password change or reset, patient archived) takes effect on the next request, which a stateless JWT could not do.
- Sessions have a **scope**: `crm` for staff and `app` for patients. CRM routes refuse app tokens and the reverse.
- **Service accounts** (machine-to-machine) use expiring, rotatable API keys (`X-API-Key`), hold service-only roles, and act under their own audit identity.
- **MFA-ready:** `users.mfa_enabled` exists; password-only login is refused with `MFA_REQUIRED` when it is set. The second-factor step and an external identity provider (`users.idp_subject`) are backlog items.
- Login, refresh and password reset are **rate limited** (per IP+email and per IP). App routes are limited per user, and the public signed-link routes per IP.

## Permission strategy

Three layers, all server-side, default deny:

1. **Route permission.** Every route declares the permission keys it needs (`require(...)` / `require_any(...)`). A test walks every route and fails if one is reachable without authentication. A missing permission is `403 FORBIDDEN` and is audited.
2. **Tenant.** Every query is limited to the caller's `organisation_id`.
3. **Object level.** Each module decides which rows the caller may see, reusing one rule for patients (`patients/access.py`):
   - `patients:read_all` sees every patient of the organisation.
   - `patients:read_assigned` sees only patients with an **active assignment** to the caller, directly or through a team they belong to.
   - Appointments, notes, documents, notifications and the timeline are visible only when their patient is visible; tasks when you own/created them or their patient is visible (or with `tasks:read_all`).

A record the caller may not see answers **404, exactly like an id that does not exist**, so guessed UUIDs reveal nothing. When the id is real, the attempt is audited as `access.denied`. List filters narrow the caller's scope and can never widen it, and pagination is applied after the scope.

## Data minimisation

- **Explicit request and response models** for every endpoint. Request models reject unknown fields (`extra="forbid"`, so no mass assignment); responses are built from allow-listed fields, never from the database row.
- **Field classification on patients:** MRN, date of birth and address are *sensitive*. They are `null` (with `sensitive_fields_hidden: true`) without `patients:read_sensitive`, and cannot be searched or sorted on.
- **Visibility classes for notes and documents:** `INTERNAL` (CRM staff with read permission), `CLINICAL` (also needs `notes:read_clinical`, so support roles and the app never see it) and `APP_VISIBLE` (also shown to the patient). Writing or uploading CLINICAL content needs the clinical permission too. Revisions in a class the caller cannot read are hidden, so reclassifying a note never exposes its earlier restricted text.
- **The patient app** has its own response models: no internal notes, staff ids, MRN or audit fields.

## Audit strategy

- One append-only table, `audit_events`. A database trigger rejects `UPDATE` and `DELETE`, so normal application code cannot edit history.
- **Recorded:** logins (success and failure), refresh, logout, password reset and change, token-reuse detection, access denied (missing permission and hidden records), user, role and team changes, every create, update, state change or archive of patients, appointments, tasks, notes and documents, full patient reads and timeline reads, reads that returned CLINICAL notes, document upload intents, uploads, rejections, download links and downloads, consent changes, notification requests and permanent failures, device registration, and audit searches themselves.
- **Content:** actor (user and type: STAFF/PATIENT/SERVICE/SYSTEM), action, resource type and id, outcome (SUCCESS/FAILURE/DENIED), the *names* of changed fields (never values), filtered metadata (ids, codes), IP, user agent and request id. Metadata keys that look sensitive are dropped. Tests check that passwords, tokens, reset codes, document content, note text and patient identifiers never appear.
- Change and audit event are written **in the same transaction**, so they are saved together or not at all. Failures and denials are written in their **own** transaction, so they survive the rollback of the failed request.
- `GET /api/v1/audit-events` (`audit:read`) filters by actor, action (or prefix), resource, outcome and time. Each search is itself audited.
- Domain history that is part of the record lives next to it: `appointment_events`, `note_revisions`, `consent_records`, `notification_attempts` (all append-only).

## Patients and assignments

- **Duplicates.** An MRN is unique within an organisation (`409 DUPLICATE_IDENTIFIER`, enforced by a unique index). The same first name, last name and date of birth gives `409 POSSIBLE_DUPLICATE`, which staff can override with `confirm_not_duplicate: true` after checking. The error never names the other record.
- **Archive, never delete.** Archiving keeps the record (retention), hides it from default lists, makes it read-only, and deactivates and signs out the patient's app account.
- **Assignments** keep their history: unassigning sets `active = false` and `ends_on`. Partial unique indexes allow one active PRIMARY per patient and stop the same person or team being assigned twice.

## Appointments and tasks

- **Appointment lifecycle:** `SCHEDULED → CONFIRMED | CANCELLED | COMPLETED | NO_SHOW`, `CONFIRMED → CANCELLED | COMPLETED | NO_SHOW`; the rest are final. Anything else is `409 INVALID_TRANSITION`. Outcomes can only be recorded once the appointment has started. Rescheduling returns a confirmed appointment to SCHEDULED. Cancelling needs a reason. Every step goes to append-only `appointment_events` and the audit log.
- **No double booking:** a PostgreSQL exclusion constraint (`btree_gist`) refuses overlapping live appointments for the same staff member, even under concurrent requests (`409 APPOINTMENT_CONFLICT`).
- **Time zones:** instants are stored in UTC; the IANA zone is kept so the app shows local time correctly across daylight-saving changes (`starts_at_local`).
- **Tasks:** `OPEN ↔ IN_PROGRESS`, then `DONE` (records `completed_at` and `completed_by`, enforced by a constraint) or `CANCELLED`; both can be reopened. Care staff can see follow-ups about their patients but can change only their own.
- **CRM summary** counts use the same scopes as the lists, and "today" is the organisation's local day.

## File storage

- **Private adapter** (`app/storage.py`): `LocalStorage` writes under `STORAGE_DIR`, which must never be served by a web server. Keys are random (`<organisation>/<32 hex>`), never file names. An S3/Azure/GCS adapter implements the same five methods with a private bucket.
- **Upload:** (1) `POST /patients/{id}/documents` declares name, type and size and returns a single-use signed upload link, (2) `PUT` the bytes to it, (3) `POST /documents/{id}/confirm` checks the size, the **real file signature** (a renamed executable is rejected), an optional client checksum, and runs the **malware-scan hook**. Rejected files are deleted. Only PDF, PNG and JPEG are accepted, up to `MAX_UPLOAD_BYTES`.
- **Download:** `POST /documents/{id}/download-link` returns an HMAC-signed link valid for `SIGNED_URL_SECONDS` (default 5 minutes) that names one document, one action and the user it was issued to. When it is used, the server **rebuilds that user's current principal and re-checks access**: a deactivated user, an ended assignment, an archived document or a revoked permission stops the link immediately. Knowing a document id or storage key is useless. Link creation and every download are audited, and tokens are redacted from logs.
- **Malware scanning:** `get_scanner()` returns `NoScanner` (status `NOT_SCANNED`) in sprint 1. Plug ClamAV or a cloud AV service in there; `INFECTED` files are rejected and deleted, and no infected file is ever served.
- Documents are **archived, never deleted**; the file is kept under the retention policy.

## Notification design

- **Outbox pattern:** a notification row is written in the **same transaction** as the business change (appointment booked, rescheduled or cancelled; app-visible message or document), so messages are never lost and never sent for a rolled-back change. CRM staff can also request one (`POST /notifications`).
- **Minimum necessary data:** the outbox stores ids, a template key and a channel. There is no address and no text. The address is read from the patient record at send time, and the text comes from a template that only says *that* something happened and points to the app. It never contains names, times, locations or clinical details, because SMS, push and email previews are not private.
- **Idempotency:** each row has an idempotency key unique per organisation. For automatic messages it is derived from the event (`appointment:<id>:<event>:v<version>:<channel>`); for API requests it comes from the `Idempotency-Key` header (same key with a different body is `409 IDEMPOTENCY_KEY_REUSED`).
- **Worker:** `POST /notifications/process` (the NOTIFICATION_WORKER service account) or `python manage.py process-notifications`. It leases due rows with `FOR UPDATE SKIP LOCKED` (parallel workers never take the same row) and passes the notification id to the provider as *its* idempotency key, so a worker that dies after the provider accepted a message cannot cause a second delivery.
- **Failures:** every attempt is recorded in `notification_attempts`. Temporary provider errors are retried with exponential backoff (30 s doubling, max 1 h) up to `NOTIFICATION_MAX_ATTEMPTS`, then marked FAILED and audited. The business record is never affected.
- **Preferences and policy:** channel opt-ins live on the patient (`contact_by_email/sms/push`, editable in the app). Transactional messages (about the patient's own care) follow the organisation policy `settings.notifications.transactional_ignores_opt_out`; other messages always respect opt-outs and also need the matching marketing consent. Skips are recorded with a reason (`OPTED_OUT`, `NO_CONSENT`, `NO_ADDRESS`).
- **Push devices:** `device_tokens`, registered by the app after login. They are hashed for lookup, never returned, have one owner at a time, are capped per user, and the user can revoke them.
- **Provider:** `app/messaging.py` defines the interface. The console provider is used until real credentials exist.

## Consent

Every change is a **new append-only row** that points to the one it replaces. The current state of a type is its latest row. Each row records status, source (APP, STAFF_VERBAL, PAPER_FORM, ...), policy version, captured_at (may be earlier than recorded, e.g. a paper form), expiry, who captured it and whether that was staff or the patient, plus optional evidence (a document). Patients can change only app-managed types (app terms, marketing email/SMS, research contact); re-sending the current state is a no-op, so app retries never duplicate evidence.

## The patient app boundary

All app routes live under `/api/v1/app`, accept only `app`-scope sessions with `app:self`, and are rate limited per user. **No app URL contains a patient or user id** (a test enforces this): every query starts from the caller's own patient record, and only records explicitly marked for the app are returned (app-visible appointments, notes and documents). Another patient's appointment or document id gives the same 404 as a random id. Profile updates use an allow-list: preferred name, phone, language and channel preferences. Legal name, date of birth and address are changed by staff after verification.

## Data lifecycle

`organisations.settings.retention` holds placeholders for retention periods (patient records, audit events, notifications) and `delete_on_app_account_closure: false`: closing an app account never deletes the health record. Patients, documents and notes are archived or retracted, never hard-deleted. Retention, anonymisation and legal-hold jobs are backlog items ([BACKLOG.md](BACKLOG.md)).

## Indexes

Each list filter and visibility check has an index. Checked with `EXPLAIN` during hardening:
patient name search (`idx_patients_name_search`, trigram), patient lists (`idx_patients_org_status`),
the assigned-to-me check (`uq_assignment_active_staff`, `idx_assignment_team`), overdue/open tasks
(`idx_tasks_org_status_due`, `idx_tasks_owner_open`), appointments by day and staff
(`idx_appointments_org_start`, `idx_appointments_staff`), notes/documents/consents per patient,
audit searches (organisation + time/actor/resource/action) and due notifications
(`idx_notifications_due`). Load testing against real volumes is a backlog item.
